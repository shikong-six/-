# 踩坑记录：axios 流式请求 timeout 的语义和直觉相反

## 问题现象

- 给流式请求（`responseType:'stream'`）加超时保护时，第一反应是担心："答案要生成 20-60 秒，timeout 设 120 秒会不会把正常的长回答掐断？"
- 查文档 + 实测后确认：**不会**。但理解错的人很容易要么不设超时（连接挂死没人管），要么把 timeout 当成"总时长限制"乱设大值。

## 问题原因

axios 的 `timeout` 语义是"**请求发出到响应头到达**的最长等待时间"，不是"整个响应体读完的限时"。

流式响应的头（200 + `text/event-stream`）在 Kimi 开始生成前就到了，之后的数据块不受 timeout 约束。所以：

- 非流式请求：timeout 限制的是整个生成时间（Kimi 卡了 120s 就抛错）——**需要设**；
- 流式请求：timeout 只约束"建连 + 拿到头"，生成多久都行——设 120s 是安全的，还能防住"Kimi 连响应头都不回"的死连接。

## 解决方法

两个调用都设 `timeout: 120000`（kimi.ts 的非流式和流式各一处），含义不同但取值都安全。

如果确实要限制流式总时长（比如防止单个请求无限挂），得自己用 `setTimeout` + `stream.destroy()` 实现，axios 管不到那一段。

## 经验总结

- 用超时保护前先搞清楚这个库的 timeout 量的是"哪个阶段"，不同库、同一库的不同响应模式，语义都可能不一样。
- 流式场景拆成两段看：建连/等头阶段（axios timeout 管）+ 数据流阶段（自己管）。
