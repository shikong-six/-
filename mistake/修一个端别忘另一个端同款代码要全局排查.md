# 修了一个端，别忘了另一个端：同款代码的修复要全局排查

## 问题

H5 真机测试发现"流式一大坨"，根因定位到 **Vue3 响应式陷阱**：占位消息是普通对象 push 进 reactive 数组，流式期间直接改原对象不触发视图更新（详见《流式渲染失效push普通对象改原引用不触发更新》）。修复时只改了 H5 的 `ChatView.vue`，Web 端没动——因为"当时只是在调 H5"。

## 为什么会漏

这个项目是**一套后端 + 两端前端**，Web 端和 H5 的聊天页是同构代码（同样的占位消息模式、同样的回调式消费、同样的 marked 渲染）。H5 的代码还是从 Web 端"移植升级"来的，同源同病是必然。但排查和修复的视角被"当前在测 H5"框住了，没有全局搜一遍同款模式。

后果：Web 端从第一版起 UI 层就没真正逐字渲染过，直到用户**在电脑上测 Web 端**才发现"怎么这边也不行"——如果用户没碰巧测到，这个 bug 可能一直带到面试现场。

## 解决方法（这次回填的内容）

以此为契机把 Web 端与 H5 的体验彻底对齐，一次补齐三件套：

1. **reactive() 包装占位消息**（根因修复，两端一致）
2. **打字机队列**：Kimi API 按块突发下发，队列 + 30ms 定时器匀速吐字；流结束 `flushTypewriter()` 冲刷剩余；切换会话/新对话时目标不在消息列表自动停
3. **status 进度事件消费**：`sendMessageStream` 加可选 `onStatus` 回调；等待提示显示"已检索到 N 条相关资料"，首 token 到达后隐藏
4. **DOMPurify 消毒**：v-html 渲染 AI 回答必须消毒（这条债从写简历"XSS 防护"那天就欠着，顺手还清）

协议层的设计红利也体现出来了：后端加 status 事件时前端"忽略未知类型"，当时 Web 端没改也不报错——现在消费端想接，加一个可选回调就完事，零破坏。

## 教训（可迁移的方法论）

**修 bug 的动作序列应该是：定位 → 修复 → `grep` 同款模式全局排查 → 各端验证。** 尤其是"同构多端"架构（一套代码复制/移植到多个端），一处病处处病。这次正确的做法是在修 H5 的瞬间就该搜：`assistantMessage.content += token` 这种写法在仓库里有几处？

另外欠账要趁手头热还清：DOMPurify 这种"知道该做但一直没做"的技术债，会跟着项目走进面试——与其被问倒，不如在每次大改动时顺手清理。

## 一句话总结

多端同构代码出 bug 时，修复动作的标准收尾是**全局搜索同款模式**（不是只修正在测的那一个端）；借修复之机把体验对齐和欠的技术债一起还清，一次提交解决一类问题。
