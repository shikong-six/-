# 踩坑记录：流式接口想给前端自增 ID，却先推了结束事件

## 问题现象

- 给答案加点赞/点踩功能时遇到顺序问题：流式问答推送给前端的事件里需要带 `historyId`（历史记录自增 ID），前端点赞时要拿它定位记录。
- 但原来的代码顺序是：**先发 `done` 事件 → 再 INSERT 历史表**——等拿到 `insertId` 时，`done` 都已经发出去了，前端早把这次请求当完成了。

## 问题原因

自增 ID 是 INSERT 成功之后才存在的。事件顺序一旦写成"推完再入库"，ID 在推送时刻根本不存在，事后也补发不了（`done` 之后前端已收尾）。

这不是流式特有的问题：**任何"响应里要带新建记录 ID"的接口，ID 的生成都必须发生在响应发出之前**。只是流式接口分多帧推送，时序问题更容易被"最后一帧才收尾"的错觉掩盖。

## 解决方法

调整顺序：**先 INSERT 拿 ID → 再推 references/session/done 事件**，session 事件里捎上 `historyId`：

```ts
// 1. 先入库（reply 已生成完，此时插入能拿到完整内容和自增 ID）
const [insertResult] = await pool.query('INSERT INTO chat_history ...');
const historyId = insertResult.insertId;

// 2. 再推结束事件（带上 ID）
res.write(`data: ${JSON.stringify({type: 'session', sessionId: sid, historyId})}\n\n`);
res.write(`data: ${JSON.stringify({type: 'done'})}\n\n`);
```

前端在 `onSession` 回调里把 `historyId` 挂到刚生成的 AI 消息上，点赞按钮据此显示。

## 经验总结

- 设计接口返回结构时，先列出"响应里每个字段什么时候才存在"，再排语句顺序——自增 ID、计算结果这类"后置产物"决定了很多代码的顺序。
- 入库失败也要优雅降级：本项目里 INSERT 失败只记日志，代价是这条回答不能点赞，不影响展示。
