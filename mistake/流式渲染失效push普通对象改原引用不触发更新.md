# 流式逐字渲染失效：普通对象 push 进 reactive 数组后直接改原对象，不触发视图更新

## 问题

H5 真机反馈"流式输出看着还是一大块"，电脑复现同样如此：发问后界面"冻结"，等十几秒后**整段答案一次性蹦出来**，中间的逐字过程完全看不到。此前以为是"Kimi 按块突发下发太快"（见《流式突发下发加打字机队列匀速吐字》），加了打字机队列后依然无效——说明病根不在呈现节奏，在**视图根本没更新**。

## 排查与验证

写了个 30 行的 effect 实验（`h5/_reactivity_test.mjs`）验证 Vue 3 的响应性行为：

```
初始渲染次数: 1
原对象直接修改后, effect 触发次数: 1 → 没触发!视图不会更新
代理对象修改后, effect 触发次数: 2 → 触发,视图更新
reactive 包过的对象直接修改, effect 触发次数: 2 → 触发,视图更新
```

铁证如山。

## 原因

Vue 3 的响应式基于 **Proxy**：依赖追踪和更新触发都只发生在**通过代理读写**时。

页面的写法是：

```ts
const assistantMsg = {role: 'assistant', content: ''};  // 普通对象
messages.value.push(assistantMsg);                       // push 进 reactive 数组
// 流式回调里：
assistantMsg.content += token;  // 直接改原对象——绕过了 Proxy，没有任何通知
```

模板渲染时通过数组代理拿到的是** reactive 代理**（和原对象是两个引用，共享底层数据）。之后直接改原对象：数据确实变了，但 proxy 的 set 陷阱没被踩到 → 没有 trigger → 组件不重渲。

流结束时答案为什么又能显示？因为那时某个 tracked 的 ref 翻转了（`streaming`/`loading` 归 false），组件重渲，模板经代理读到了**已经攒完整的全部内容**——所以看起来就是"一大坨"。status 文案不切换、打字机无效，全是同一个根因。

**注意：Web 端从第一版起就是这个写法，UI 层从未真正逐字渲染过**。之前"已验证：198 个 token 分批到达"验证的是**网络层事件**，没人盯着屏幕看 UI 是不是逐字更新——教训：流式功能必须"肉眼验收"，不能只看数据。

## 解决方法

创建占位消息时用 `reactive()` 包一层再 push：

```ts
const assistantMsg = reactive<DisplayMessage>({role: 'assistant', content: ''});
messages.value.push(assistantMsg);
assistantMsg.content += token;  // 现在改的是代理，正常触发更新
```

数组访问时 Vue 会复用同一个代理（按原始对象缓存），所以后续经数组拿到的和手里的是同一个响应式引用，行为一致。

## 一句话总结

Vue 3 里"push 进 reactive 数组的**普通对象**，之后直接改这个对象引用"不会触发视图更新——依赖通知只走 Proxy。要拿着引用持续修改的对象，创建时就 `reactive()` 包一层；验证流式 UI 必须肉眼盯着屏幕看，网络层"事件分批到达"不等于用户看到逐字输出。

## 勘误

本篇是《流式一大坨冒出来是首字延迟不是代理缓冲》和《流式突发下发加打字机队列匀速吐字》的**根因修正**：首字延迟真实存在（status 事件仍有价值），打字机队列也仍有价值（抹平 API 突发节奏），但"一大坨"的主因是本次的响应式 bug——修复 reactive 后即使不加打字机也能看到逐字渲染。两个旧方案都保留，各自解决真实存在的问题，叠加后才是完整体验。
