# 踩坑记录：客户端断开后 Kimi 还在白跑（并发额度被占死）

## 问题现象

- 流式问答场景：用户关闭页面/中途离开，浏览器断开 SSE 连接——但后端到 Kimi 的生成**不会停**，Kimi 把答案跑完为止。
- 对本项目这是致命的：Kimi 免费账号**并发上限 1**，前一个断开的请求把额度占满跑完，期间所有人的新提问全部失败。

## 问题原因

后端没有任何"客户端还在不在"的感知。Kimi 流是后端主动发起的独立 HTTP 连接，浏览器断开只是断了后端→浏览器这一段，后端→Kimi 那段不受影响，自然跑到底。

## 解决方法

两步配合：

1. **监听响应关闭**：`res` 的 `close` 事件在连接断开时触发；但要排除"正常走完"的情况（正常结束也会 close），用 `res.writableEnded` 区分：

```ts
let clientGone = false;
res.on('close', () => {
  if (!res.writableEnded) clientGone = true;  // 正常 end() 的不算断开
});
```

2. **把取消检查传进生成循环**，每收一块数据查一次，取消就销毁 Kimi 流：

```ts
// chatWithKimiStream 的 data 事件里
if (isCancelled?.()) { response.data.destroy(); return; }
```

3. 断开后残缺的回复**不入历史库**（不完整的数据进了库就是脏数据）。

## 经验总结

- 流式接口是"两个连接夹一个生成过程"：客户端↔后端、后端↔上游。任何一个断了都要考虑另一个怎么办。
- 凡是"上游资源按并发收费/限流"的场景，中止传播（把取消信号传回上游）都是必做项，不只是体验问题，是资源问题。
- `res.on('close')` + `writableEnded` 是 Node 里区分"断开"和"正常结束"的标准姿势。
