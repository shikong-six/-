# H5 流式问答"一大坨冒出来"——不是代理缓冲，是大模型首字延迟

## 问题

H5 真机测试时发现：提问后答案不是逐字输出，而是等了很久之后"一大坨"一次性冒出来。第一反应是 Vite devServer 代理缓冲了 SSE（Web 端 webpack 踩过一模一样的坑：`compress` 中间件攒住流）。

## 排查过程

写了个逐事件计时脚本（fetch 读流，记录每个事件的到达时刻），同问题分别打**直连后端 3000**和**经 Vite 代理 8081**：

```
直连 3000：  首 token +22.8s → 结束 +34.8s（生成阶段约 12 秒，事件逐批到达）
经 8081：    首 token +18.1s → 结束 +23.3s（生成阶段约 5 秒，事件逐批到达）
```

两个结论同时浮出水面：

1. **代理没问题**：走代理的事件有真实时间差（18.1s → 18.5s → 23.3s），没有攒批
2. **真正的元凶是首字延迟**：Kimi 免费档发问后要排队 **18~23 秒**第一个 token 才出来；且 Moonshot API 的流式是**按块下发**的（前 8 个 token 同一时刻到达），不是逐字。生成阶段本身很快（约 27 token/秒），所以体感就是"干等 20 秒 → 答案几秒内涌完"

## 解决方法

**把"干等首字"拆出一段可见进度**：

1. **后端推 status 事件**：RAG 检索在 1~3 秒内就能完成，所以在 `houduan/src/routes/chat.ts` 的 `/stream` 路由里，检索完成后、调 Kimi 之前先推一条 `data: {"type":"status","message":"已检索到 N 条相关资料…"}`。等待被拆成"检索完成（+3s 有反馈）→ 生成中"两段
2. **前端消费 status**：H5 的 `useChatStream` 加 `onStatus` 回调，等待提示文案由它更新；提示语配省略号滚动动画证明页面没卡死
3. **协议兼容性**：Web 端前端忽略未知事件类型，后端改动对旧客户端零影响（这也体现了当初设计事件协议时按 type 分发的好处）

效果验证：status 事件 +2.8s 到达，首 token +16.9s——用户在第 3 秒就知道"检索到 3 条资料，正在生成"，而不是对着一行静态文字干等 20 秒。

## ⚠️ 勘误（后补）

本篇对"一大坨"主因的诊断**不完整**。后续发现更根本的原因：H5 聊天页的占位消息是普通对象直接 push 进 reactive 数组，流式期间改原对象不触发视图更新，答案到流结束才整段蹦出——详见《流式渲染失效push普通对象改原引用不触发更新》。首字延迟与 status 事件是真实存在的问题，方案保留；但"一大坨"的主因是那个响应式 bug。教训：流式 UI 必须肉眼验收，网络层事件到达 ≠ 用户看到逐字输出。

## 一句话总结

流式"一大坨"先别赖代理，用计时脚本区分"首字延迟"和"传输缓冲"；大模型免费档首字排队十几秒是常态，解法是检索完成后先推一条进度事件，把无反馈的等待拆开——事件协议按 type 分发的设计让这种扩展不影响旧客户端。
