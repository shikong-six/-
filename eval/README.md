# 评测（eval/）

**为什么要有这个目录**：项目里有 RRF 融合、多事项拆分、本机重排、相关性闸门这些设计，
但如果不做评测，就说不清**哪一步真的有用**、效果是好是坏。
有了它才能给出可证伪的结论，例如："补了口语同义词后，多事项用例的文档召回从 × 变 √，
整体文档召回 88% → 96%"。

## 文件

| 文件 | 作用 |
|---|---|
| `run_eval.py` | 主脚本：24 条分类题库 + 5 个指标，两种模式（`--full` 端到端 / `--retrieval-only` 只打检索接口） |
| `audit_golden.py` | **题库体检**：逐条核对期望文档 / 期望法条 / 要点在这个语料库里能不能达成。**加题或改语料后先跑它**，否则会把"尺子量不到的东西"算成系统缺陷 |
| `compare_reports.py` | 新旧报告对比：总指标（同时给「整份报告」与「同口径」两栏）+ 分类对比 + 逐条变化 |
| `probe_sse.py` | **零 token 探针**：只读 `/api/chat/stream` 检索阶段的状态事件，判断线上后端加载的是哪一版代码（改完检索逻辑先跑它，避免拿旧代码的结果下结论） |
| `ingest_docs.py` | 把新法律文档入库（本地预检条文号能否切块 + 关键内容是否存在 → 再走 `/api/knowledge/upload`） |
| `report-*.json` | 历史报告，每轮一份，**旧文件不覆盖**，便于对照 |

## 怎么跑

```bash
cd eval
# 端到端（会调模型，约 20 分钟 / 24 条）
python run_eval.py --full --user <账号> --password <密码> --sleep 20
# 只打知识库检索接口（几乎不花 token）
python run_eval.py --retrieval-only
# 题库体检（不花 token）
python audit_golden.py
# 对比两轮报告
python compare_reports.py report-1014-1816.json report-1014-1848.json
```

▶ **Windows 后台 / 重定向跑时，必须先设 `PYTHONUTF8=1`**：
脚本里要 `print("⚠样本少")`，而 stdout 被重定向时编码是 GBK，`⚠`(U+26A0) 编不出来会抛
`UnicodeEncodeError` —— 而且崩在报告落盘**之前**，整轮白跑。在窗口里直接跑没事（控制台走 UTF-8）。

```powershell
$env:PYTHONUTF8='1'; python run_eval.py --full --user <账号> --password <密码> --sleep 20
```

## 五个指标怎么算的

| 指标 | 判据 | 谁决定 |
|---|---|---|
| 文档召回率 | 期望文档是否出现在**后端返回的引用列表**里；多事项要求每件事的文档都命中 | 检索 |
| 条文命中率 | 期望条文号是否出现在引用原文里（民法典有 1260 块，"命中了民法典"几乎等于没标准） | 检索 |
| 引用正确率 | 回答里写的「第X条」是否都在给定资料中 —— **编造就扣分** | 生成 |
| 要点覆盖率 | 回答是否覆盖标准要点；比对前**先去掉虚词**（否则照抄法条原文会被判 0%） | 生成 |
| 拒答率 | 库里没有的问题，是否正确说「未找到依据」而不是硬答 | 生成 |

五个指标全部由脚本按确定性规则计算，**不用大模型当裁判**。

## 三个必须知道的坑

1. **`--retrieval-only` 测的不是 RAG 链路**。它打的是知识库裸检索接口，
   **不经过 RRF 融合、本机重排、多事项拆分、相关性闸门**。
   验证检索侧的改动必须走 `--full`，否则数字看起来"差不多"，结论却是错的。
2. **题库一变，百分比就不能直接比**。分母不同会凭空多出几个点（18 题的 78% 和 20 题的 85%）。
   `compare_reports.py` 会同时给「整份报告」和「同口径（只算两轮共有的题）」两栏，看后者。
3. **要点覆盖率会因模型措辞抖动而翻转**。同一道题、引用完全相同，三轮实测是 100% → 50% → 100%
   （模型换了分段方式，没写"危险驾驶"这个词，而该词在语料里出现 0 次）。
   所以四个指标里最可信的是前三个，要点覆盖要交叉看，别只看总分。
